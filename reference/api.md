# SEVA backend API

The nineteen HTTP endpoints a SEVA client calls, the shapes they take and return, and the rules they
enforce. Written for the client team: everything here is observable from outside, and nothing here
describes the database.

This document is generated by hand from the code and kept beside it. Where it disagrees with
`supabase/functions/`, the code is right and this is a bug — the specification's §7 is the authority
for *what* should exist, this is a description of what does.

Version 1, 12 October 2026.

---

## 1. How to call it

Every endpoint is an Edge Function on the project host:

```
https://<project-ref>.supabase.co/functions/v1/<path>
```

Three headers on every request:

| Header | Value | Why |
| --- | --- | --- |
| `apikey` | `sb_publishable_…` | The project's publishable key. Never the secret key — that one is for workers and would bypass every row-level rule. |
| `Authorization` | `Bearer <access token>` | The signed-in person's GoTrue access token. Omit only on `GET /discover*`. |
| `x-region` | `ap-south-1` | SEVA runs in Mumbai only. A request without it still works; one with a different region is a client bug worth catching in review. |

**Every `POST` also needs `Idempotency-Key`**, a UUID the client generates per logical action and
reuses on retry. See §3.

Timestamps are ISO 8601 **with an offset** — `2026-10-21T07:00:00+05:30`. A timestamp without one is
rejected, because reading it in the server's timezone would silently move an Activity by hours.
Dates are `YYYY-MM-DD`.

### Getting a token

Sign-in is phone OTP through Supabase Auth, not through this API:

```
POST /auth/v1/otp          { "phone": "+919812345678" }
POST /auth/v1/verify       { "phone": "+919812345678", "token": "123456", "type": "sms" }
                           -> { "access_token": "…", "refresh_token": "…" }
```

Staff additionally enrol a TOTP factor and verify it, which raises the session to `aal2`; every
`admin_*` function refuses an `aal1` token. That flow is `/auth/v1/factors`, `…/challenge`,
`…/verify`, and it is Supabase's, not SEVA's.

## 2. Errors

One shape, always:

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "title is missing or malformed.", "retryable": false } }
```

`code` is for the client to branch on, `message` for a person to read, `retryable` for whether
trying again can possibly help. **Branch on `code`, never on the message** — messages change.

| Code | HTTP | Retryable | Means |
| --- | --- | --- | --- |
| `VALIDATION_FAILED` | 400 | no | A field is missing or malformed; `message` names it. |
| `UNAUTHENTICATED` | 401 | no | No token, or a token this project did not sign. |
| `ONBOARDING_REQUIRED` | 403 | no | Signed in, but `POST /account/onboarding` has not run. |
| `AGE_RESTRICTED` | 403 | no | Under 18, on something 18+ only. |
| `FORBIDDEN` | 403 | no | Not yours, or your account is suspended. |
| `NOT_FOUND` | 404 | no | Missing, or not visible to you. The two are deliberately the same answer. |
| `ACTIVITY_FULL` | 409 | no | At capacity. |
| `ACTIVITY_NOT_JOINABLE` | 409 | no | Cancelled, already started, or not yet screened. |
| `IDEMPOTENCY_KEY_REUSED` | 422 | no | That key was used for a different request body. |
| `EVIDENCE_REQUIRED` | 422 | no | A metric was claimed with no photo. |
| `METRIC_OUT_OF_RANGE` | 422 | no | A claimed metric is outside its per-Act bound. |
| `DAILY_LIMIT_REACHED` | 429 | no | Today's allowance for this action is used up. Resets at midnight IST. |
| `RATE_LIMITED` | 429 | **yes** | Too fast. Honour `Retry-After`. |
| `FEATURE_DISABLED` | 503 | **yes** | A kill switch is engaged. Try later; do not discard the user's input. |
| `INTERNAL` | 500 | **yes** | A fault on our side. Safe to retry with the same idempotency key. |

A `429` carries `Retry-After` in seconds. `RATE_LIMITED` is a short window and worth retrying;
`DAILY_LIMIT_REACHED` is not retryable today and the client should say so rather than spin.

---

## 3. Idempotency

Every `POST` takes `Idempotency-Key: <uuid>`. Generate it when the person taps the button, not when
the request goes out, and reuse it for every retry of that tap.

- **Same key, same body** → the original result, with `200` instead of `201`.
- **Same key, different body** → `422 IDEMPOTENCY_KEY_REUSED`.
- **No key** → `400`, naming `Idempotency-Key`.

A replay is not counted against your rate limit. This is what makes a flaky connection safe: retry
until you get an answer, and you cannot create two Acts.

`201` means a row was created. `200` on a `POST` means nothing was created — either a replay, or an
action that folded into something already on file (see `POST /reports`).

---

## 4. Rate limits

Three windows run at once — per minute, per hour, per day — and the day boundary is midnight
**Asia/Kolkata**. Limits are per person. **They are halved for an account less than 72 hours old.**

The per-route allowances are in each endpoint below. A refused request is still counted; a replay is
not.

## 5. Endpoints

### 5.1 Account

#### `POST /account/onboarding`

Signed in · once per account

Creates the profile. **Until this succeeds, every write returns `ONBOARDING_REQUIRED`** — it is the
gate the whole API hangs off.

```json
{
  "display_name": "Anand Rao",
  "date_of_birth": "1994-03-11",
  "terms_version": "2026-10-01",
  "privacy_version": "2026-10-01"
}
```

`201` with the profile. Calling it again is answered `200` with the profile already on file, not an
error — so a client that loses the response can simply call again.

Refusals: under 13 is `VALIDATION_FAILED` on `date_of_birth`. A date of birth more than 150 years
ago is treated as a typo and refused the same way. The date of birth is stored where only its owner
can read it and is never returned by any other endpoint.

#### `POST /account/delete`

Signed in · 3/day

Schedules erasure. `202` with `{ "deletion": { "status": "pending", "requested_at": … } }`. Asking
again while one is pending is answered with the request already on file.

The work happens out of band, usually within the hour. Content that was removed or held for a rule
breach is kept as a record for 180 days; everything else goes, and the account can no longer sign in.
Asking does not require onboarding — the right to be erased does not begin at onboarding.

#### `POST /account/export`

Signed in · 2/day

`202 { "export_id": "<uuid>" }`. The file is built out of band. Poll the next endpoint.

#### `GET /account/export/:id`

Owner · 30/h

```json
{ "status": "pending" }
{ "status": "ready", "url": "https://…" }
{ "status": "expired" }
{ "status": "failed" }
```

The URL is signed for one hour; the file itself is deleted after seven days, after which this
answers `expired`. It contains the person's profile, Acts, Activities, participation, supports,
blocks, points ledger and the reports they filed.

It does **not** contain their phone number or email address — both live in Supabase Auth, and the
app already shows them on the account screen. Whether an export must include them is an open legal
question for the program.

### 5.2 Uploads

Three steps, in order. You cannot attach a photo to an Act until step 3 has run.

#### `POST /uploads`

Onboarded · 30/h · 100/day

```json
{ "purpose": "act" }     // or "activity", or "avatar"
```

`201`:

```json
{
  "photo": { "id": "<uuid>", "status": "uploading" },
  "upload_url": "https://…"
}
```

#### Step 2 — `PUT` the bytes

`PUT` the file to `upload_url` with `Content-Type: image/jpeg`. This is Supabase Storage, not SEVA.
The URL is one-time.

**JPEG only, at most 5 MB, at most 2048 px on the long edge.** Resize and re-encode on the device:
the bucket refuses anything else, and the check reads the declared content type, so mislabelling a
PNG will fail later rather than here.

#### `POST /uploads/:id/complete`

Owner · 60/h

No body. `200 { "photo": { "id": …, "status": "processing" } }`.

Confirms the object arrived and queues screening. Calling it twice is safe: the second call returns
the status the photo already has and queues nothing.

If the object is missing or too large, `400` naming `file`, and the photo stays in `uploading` where
a sweep collects it after 24 hours.

A photo is **not published** when this returns. It becomes publicly readable only after screening
passes, which also sets a profile photo if the purpose was `avatar`. Clients can never set an avatar
directly.

### 5.3 Acts

#### `POST /acts`

Onboarded · 10/h · 30/day

```json
{
  "title": "Cleared the lake shore",
  "story": "Eleven of us filled fourteen sacks along the east bank before the rain came in.",
  "category": "environment",
  "occurred_on": "2026-10-09",
  "lon": 73.8567,
  "lat": 18.5204,
  "activity_id": "<uuid>",
  "photo_ids": ["<uuid>"],
  "metrics": { "waste_kg": 48.5 }
}
```

`activity_id`, `photo_ids` and `metrics` are optional. `201` with the Act, whose `status` is
`pending`.

- **A claimed metric needs a photo.** Without one, `422 EVIDENCE_REQUIRED`.
- Metrics outside their per-Act bound are `422 METRIC_OUT_OF_RANGE`.
- `photo_ids` must be photos you uploaded and completed.
- **The location you send is coarsened before it is stored** — to roughly a 5 km grid. Measured: a
  point in Pune was stored 2,366 m from what the client sent. No endpoint ever returns an exact Act
  location, including to its author. Send the real coordinate; do not pre-round it.

An Act is invisible to everyone but its author until screening passes, at which point points are
awarded.

#### `PATCH /acts/:id`

Author · 30/h

```json
{ "title": "Cleared the lake shore", "story": "Eleven of us filled fourteen sacks…" }
```

Either field alone is fine; sending neither is `400` naming `body`. `200` with the Act.

**An edit sends the Act back to `pending` and re-screens the text**, so it disappears from other
people's feeds until it passes again. Say that in the interface before the person taps save — it is
the single most surprising behaviour in this API. Points already awarded are not taken back.

Only the author, and only `title` and `story`. The category, the date, the location, the photos and
the metrics are fixed once created: a claim with evidence attached cannot be quietly rewritten into
a different claim.

### 5.4 Activities

#### `POST /activities`

Onboarded, **18+** · 5/day

```json
{
  "title": "Lake shore cleanup",
  "description": "Bring gloves and water. We meet at the east gate and finish before noon.",
  "category": "environment",
  "starts_at": "2026-10-21T07:00:00+05:30",
  "ends_at": "2026-10-21T10:00:00+05:30",
  "lon": 73.8567,
  "lat": 18.5204,
  "location_label": "East gate",
  "capacity": 25,
  "what_to_bring": "Gloves, water, a hat",
  "photo_ids": ["<uuid>"]
}
```

`what_to_bring`, `photo_ids` and `campaign_id` are optional. `201`, status `pending`.

Under-18 accounts get `403 AGE_RESTRICTED`: organising means strangers coming to a place you named.

**An Activity's meeting point is stored and served exactly**, unlike an Act's — people have to be
able to find it. Say so in the interface if that matters to the organiser.

#### `POST /activities/:id/join`

Onboarded · 30/h

No body. `200 { "joined_at": …, "already_joined": false, "participant_count": 1 }`.

Joining twice is not an error — `already_joined` is `true` and nothing changes. `409 ACTIVITY_FULL`
at capacity; `409 ACTIVITY_NOT_JOINABLE` if it is cancelled, already started, or not yet screened.

#### `POST /activities/:id/leave`

Participant · shares the join limit

No body. `200`. Frees the place immediately.

#### `POST /activities/:id/cancel`

Organiser · 5/day

```json
{ "reason": "the lake level rose after the rain" }
```

`200 { "notified": 1, "cancelled_at": … }`. Everyone who joined is emailed, or sent an SMS if they
have no email address. `notified` is how many messages were queued, not delivered.

A cancelled Activity stays readable by its direct link, because the link is already in people's
hands, and stops appearing in Discover.

### 5.5 Reports

#### `POST /reports`

Signed in · 20/day

```json
{
  "subject_type": "act",
  "act_id": "<uuid>",
  "reason": "misleading",
  "details": "the sack count does not match the photo"
}
```

`subject_type` is `act`, `activity` or `profile`, and you must send exactly the matching id field —
`act_id`, `activity_id` or `reported_user_id`. `details` is optional, 500 characters.

`201` with the report. **`200` means you already have an open report on that subject**, and the
answer is the one on file; sending a more serious reason upgrades it rather than creating a second.

Nothing in the response says whether the report caused anything to happen. That is deliberate: a
client that could see a threshold fire could find the threshold.

Reporting does not require onboarding beyond having a profile, and a suspended account may still
report — the duty to carry a complaint does not depend on the complainant's standing.

### 5.6 Discover — no token needed

#### `GET /discover?lon=&lat=&radius_km=&category=&cursor=&limit=`

Anyone · 60/min per person or IP

Nearby upcoming Activities. `lon` and `lat` are required; `radius_km` defaults and is snapped to a
rung; `limit` is clamped.

```json
{
  "activities": [
    {
      "id": "…", "title": "…", "category": "environment",
      "starts_at": "…", "ends_at": "…",
      "lon": 73.8567, "lat": 18.5204, "location_label": "East gate",
      "capacity": 25, "participant_count": 1,
      "distance_m": 0, "organiser_id": "…", "campaign_id": null
    }
  ],
  "next_cursor": null
}
```

**Answers are cached for 60 seconds** per cell, radius, category, cursor and page length. Two
different people asking the same question get the same cached page; blocked authors are removed
after the cache, per reader. A newly published item can take up to a minute to appear — that is the
cache, not a failure.

#### `GET /discover/activities/:id`

Anyone · 60/min. One Activity, for a shared link. Still served after cancellation.

#### `GET /discover/campaigns` · `GET /discover/campaigns/:id`

Anyone · 60/min. Active campaigns and their progress.

#### `GET /discover/health`

Anyone · no limit. `{ "status": "ok" }` or `{ "status": "degraded" }` and nothing else.

`degraded` means a moderation or job backlog that operations need to see. **It does not mean the API
is down** — show the offline state only when this endpoint cannot be reached at all.

### 5.7 Feed

#### `GET /feed?lon=&lat=&radius_km=&category=&cursor=&limit=`

Signed in · 60/min

Recent published Acts near a location, with blocked authors removed.

```json
{
  "acts": [
    {
      "id": "…", "author_id": "…", "title": "…", "story": "…",
      "category": "environment", "occurred_on": "2026-10-09",
      "activity_id": null, "created_at": "…", "published_at": "…",
      "distance_m": 2366,
      "photos": [{ "public_path": "…", "thumb_path": null, "width": null, "height": null }],
      "metrics": { "waste_kg": 48.5 }
    }
  ],
  "next_cursor": null
}
```

Same 60-second cache as Discover. `photos[].public_path` is a key in the public `media` bucket:

```
https://<project-ref>.supabase.co/storage/v1/object/public/media/<public_path>
```

A removed photo stops being served from that bucket immediately, so treat a 400 or 404 on an image
as "gone", not as an error to retry.

## 6. Reading tables directly

Some reads go through PostgREST rather than a function, with the same `apikey` and `Authorization`
headers:

```
GET   /rest/v1/acts?select=*,act_metrics(*),media(*)&id=eq.<uuid>
GET   /rest/v1/profiles?id=eq.<uuid>
PATCH /rest/v1/profiles?id=eq.<uuid>     { "display_name": "Anand R.", "bio": "…" }
```

What you can see is enforced per row: your own rows always, plus published content, minus authors
you have blocked. A suspended person can still read their own profile, which is how a client can
tell them they are suspended and until when.

**`display_name` and `bio` are the only columns a client may write.** Points, verification, counts,
content status and the avatar are all refused with a `403` from the database, not from a function —
so do not build an interface that offers them.

Editing `display_name` or `bio` sends the profile text back for screening.

## 7. Things worth knowing before you build a screen

- **Nothing a person writes or uploads is public until it has been screened.** A newly created Act
  or Activity is `pending` and invisible to everyone else, usually for seconds. Design for it: show
  the author their own pending content, and say it is being checked.
- **`pending` is not an error state.** Neither is `processing` on a photo.
- **An Act's location is coarse and an Activity's is exact.** Do not draw an Act on a map as though
  it were a precise pin.
- **A `503 FEATURE_DISABLED` is temporary and not the user's fault.** Keep their draft.
- **`GET /discover/health` saying `degraded` is not an outage.**
- **Retry with the same idempotency key.** It is always safe and never double-charges a limit.
- **Phone numbers, dates of birth and exact Act locations are never returned by any endpoint**, to
  anyone, including their owner's own client in some cases. If a screen needs one, it is the wrong
  screen.

## 8. What is not in version 1

No search. No comments or direct messages. No following. No notifications beyond the one
cancellation message. No web upload path separate from the mobile one. No public profile endpoint —
profiles are read from the table. No route returns another person's contact details, ever.
